# Story 13.2: Room- and Power-Point-Scoped Saves

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a user editing my flat's rooms and power points,
I want saving a room to only ever touch that one room,
so that renaming or reconfiguring a power point in one room can never be silently lost because of an unrelated edit to a different room elsewhere.

## Acceptance Criteria

1. **Given** room/power-point creation, rename, and deletion currently flow only through `UpdateFlatStructureFunction.cs`'s whole-flat replace payload, **when** implemented, **then** new dedicated Functions exist, following the same per-verb pattern as Story 13.1's device endpoints and this codebase's `Features/Tariffs/` convention: `POST /v1/flats/{flatId}/rooms` (create room, accepting the room's `name`, `sortOrder`, and its **initial nested power points** — see "Gap found" #1 for why power points must be accepted at creation time, not added only via a later update), `PUT /v1/flats/{flatId}/rooms/{roomId}` (update room name and its power points' name/`plugId` — not devices, which Story 13.1 already scoped out entirely and which this story assumes are already gone from the write path), `DELETE /v1/flats/{flatId}/rooms/{roomId}` (delete room, cascading power points and devices exactly as today), each requiring the room's own current `rowVersion` (not the Flat's) and returning `409` on a concurrency mismatch — matching Story 13.1's per-entity concurrency-check pattern, not the old endpoint's Flat-level check.

2. **Given** `FlatStructureEditor.tsx`'s existing `handleSaveRoom`/`handleDeleteRoom` currently build a whole-flat payload via `toWireRequest` (backfilling every other room's data from `lastSaved`), **when** implemented, **then** these are rewired to call the new per-room endpoints directly, sending only the one room being saved/deleted — `lastSaved`'s role as a whole-flat-payload source is eliminated; each save now needs only its own room's current draft state to build its request. (`lastSaved` itself is **not** deleted — see "Gap found" #2 for why it must stay, just re-scoped.)

3. **Given** this changes what `UpdateFlatStructureFunction.cs`'s `PUT /v1/flats/{flatId}/structure` is responsible for, **when** implemented, **then** its scope is reduced to zero remaining callers and it is **removed entirely**, along with `UpdateFlatStructureValidator.cs`, the top-level bulk "Save" button, and the now-dead `UpdateFlatStructureRequest`/old `RoomInput` backend types — per this project's "delete rather than leave a shim" convention (Epic 9 retrospective's `TariffResolver` deletion precedent) and per this story's own resolution that no caller still needs a genuine whole-flat write once per-room saves cover every case, including first-time default-template persistence (see "Gap found" #1).

4. **Given** the new endpoints, **when** tested, **then** new `api.Tests/Features/FlatStructure/` test files cover each new Function's `RunAsync` directly (success, tenant-check, validation, `PlugId` uniqueness conflict per Story 11.3's existing DB-level constraint, `RowVersion` conflict), and `FlatStructureEditor.test.tsx`'s existing per-room save/dirty-state coverage (including Story 11.8's room-list save-state-consistency tests) is updated to reflect the new per-room payload shape while preserving its existing assertions about which rooms show saving/disabled state.

### Gap found during story creation

Four corrections/additions to the epic's original text (`epics/epic-13-flat-structure-save-integrity-device-and-room-scoped-saves.md#Story 13.2`), found by reading the actual current-state code (`FlatStructureEditor.tsx`, `draftModel.ts`, `UpdateFlatStructureFunction.cs` — all read in full during story creation) rather than trusting the epic's prose alone:

**1. The epic's literal AC1 text ("create room") omits that a brand-new room's *first* save can already carry drafted power points — and that gap is exactly why the whole-flat bulk-save button can be deleted, not just shrunk.** `RoomEditor.tsx`'s `handleAddPowerPoint` lets a user add power points to a **never-yet-persisted** `DraftRoom` (via local `onChange`, no network call) before ever clicking that room's own Save button. When they do click Save, `handleSaveRoom`'s `room.originalName === undefined` branch treats it as a create — and the room may already have one or more power points in its draft. So `POST /rooms` must accept a nested `powerPoints` array on creation, not just `name`/`sortOrder`. This closes the loop the epic left open ("the initial default-template seeding flow... if any remain"): the app's five `createDefaultDraftRooms` rooms are also never-yet-persisted `DraftRoom`s with the same shape, and **each already has its own per-row Save button** in the list view (`FlatStructureEditor.tsx`'s room list, the `Check`-icon button calling `handleSaveRoom(room)` directly) that's enabled the instant a room exists locally (`isRoomDirty` returns `true` unconditionally when `originalName` is `undefined`). Once `handleSaveRoom` is rewired to call the new per-room `POST`/`PUT` instead of the whole-flat endpoint, **every scenario the old bulk "Save" button covered — including first-time default-template persistence — is already covered by clicking each room's own existing Save button.** The bulk button, `handleSave`, `toUpdateRequest`, `hasNoRooms`, and the page-level `hasPlugIdConflict`/`hasEmptyName` banners it gated all become dead weight tied to a no-longer-necessary action, not a feature to preserve — remove them (Task 7). The equivalent, more precise per-room warnings (`isSaveBlocked`, already rendered inline per row) fully cover the same information at the point where it's actionable.

**2. `lastSaved`/`KeyedRoomInput` stay — only their role changes.** The epic's AC2 text says "`lastSaved`'s role as a whole-flat snapshot used to backfill other rooms' payload data is eliminated," which could be misread as "delete `lastSaved` entirely." It can't be: `hasPlugIdConflictForRoomSave(room, lastSaved)` (unchanged, still needed) checks a room's own power points' `plugId`s against every *other* room's **last-saved** `plugId`s to catch a cross-room conflict *before* attempting a save — this is a client-side pre-check that has nothing to do with how the outgoing payload is built. `isRoomDirty(room, lastSaved)` (unchanged, still needed) is how each row's Save button decides whether it's enabled at all. Both stay exactly as-is; only `toWireRequest`/`toUpdateRequest` (the two functions that *built a full-flat payload from* `lastSaved`) are deleted. `toKeyedRooms`/`withRoomAppended`/`withRoomUpdated`/`withRoomRemoved` (which keep `lastSaved` in sync locally after each successful per-room save/delete) all stay, unchanged.

**3. `currentRowVersionRef`/`refreshRowVersionAfterConflict` become dead code and must be deleted, not left behind.** Both exist today *only* to supply/refresh the Flat's own `rowVersion` for the whole-flat payload — their sole two call sites (`handleSaveRoom`, `handleSave`, `handleDeleteRoom`) are all being rewired or deleted in this story. Post-rewire, each per-room save/delete needs that **room's own** `rowVersion` (added to the wire contract by Task 1), tracked per-`DraftRoom` (`DraftRoom.rowVersion`, present once a room is persisted, refreshed from each successful response) — not a single flat-wide ref. Leaving the old ref/refresh function in place unused would be exactly the kind of shim this project's convention rejects.

**4. Per-entity `RowVersion` scope: check the Room's own token, not the Flat's, and don't add a *second* explicit check for nested Power Points.** The old endpoint checked only `Flat.RowVersion` via `db.ApplyRowVersionCheck(flat, request.RowVersion)`; `Room`/`PowerPoint` already have their own `.IsRowVersion()` columns (`RoomConfiguration.cs`, `PowerPointConfiguration.cs`) that are *configured* but never *checked* against a client-supplied value anywhere today — Story 12.2's Dev Notes already flagged this as "a natural, acceptable side effect" of loading-and-mutating instead of blind-replace: EF's own automatic optimistic-concurrency-on-`SaveChangesAsync` already throws `DbUpdateConcurrencyException` for a *nested* Power Point that changed underneath this request, without needing an explicit second check — the existing `catch (DbUpdateConcurrencyException) → 409` handles both. This story adds one explicit, client-supplied `rowVersion` check per request: the target **Room's**, matching Story 13.1's one-token-per-request pattern exactly (Device endpoints check the Device's own token, not the Flat's or the PowerPoint's).

### Why this story exists

Sourced from `_bmad-output/implementation-artifacts/investigations/structure-editor-device-not-persisted-investigation.md` (2026-08-02) and the Epic 13 text's own framing: Story 13.1 closed the highest-frequency, highest-severity instance of the whole-flat-replace data-loss risk (devices). The identical mechanism still applies one level up — `FlatStructureEditor.tsx`'s existing per-room Save UI (`handleSaveRoom`) *looks* scoped to one room but its payload (`toWireRequest`) still carries every other room's data from the same never-resynced `lastSaved` snapshot, so a stale tab's "just this room" save can still silently revert a different room's rename or power-point edit made elsewhere in the meantime. This story closes that remaining gap and, per Task 4/"Gap found" #1, removes the whole-flat write endpoint entirely rather than leaving it as an unused, still-exploitable code path.

### The one thing Story 12.2 already fixed, and the one thing it didn't

Story 12.2's big identity-preserving upsert rework (matching `Room`/`PowerPoint`/`Device` by ID instead of blind delete-and-recreate) made row *identity* survive a save — necessary for `DeviceAssignmentPeriod` history. It did **not** close the general "anything absent from a stale payload gets deleted" risk: a stale tab's payload still doesn't include a room/power-point added by another tab, and the old endpoint still deletes anything absent from the incoming array regardless of whether IDs are preserved for what *is* present. This story (and 13.1 for devices) close that remaining risk by making each save request describe only the one resource actually being changed — nothing is ever "absent, therefore deleted," because nothing outside the target Room is ever part of the request at all.

### `PlugId` uniqueness stays a two-layer defense

The app-level within-payload duplicate check (Task 2.3/2.4, now scoped to one Room's own power points instead of the whole flat) and the DB-level filtered unique index (`IX_PowerPoints_FlatId_PlugId_NotNull`, Story 11.3, unchanged) both stay. The DB-level index is now the *only* thing catching a cross-room duplicate (two different Rooms both trying to claim the same `PlugId` in the same save round — no longer possible to check client-side within one Room's own payload, since it can't see other Rooms' current state without racing the exact staleness problem this story is fixing). This is intentional, not a regression — matches the existing `catch (DbUpdateException)` → "This Smart Plug is already assigned to another Power Point in this flat." message, copied verbatim from the old endpoint.

### Do not add per-PowerPoint `rowVersion` checks

Per "Gap found" #4 — one explicit client-supplied concurrency check per request, at the Room level, matching Story 13.1's Device-level precedent. Nested PowerPoint updates are still protected by EF's own automatic optimistic-concurrency-on-save (the existing `catch (DbUpdateConcurrencyException) → 409` already covers a PowerPoint that changed underneath the request — the same mechanism Story 12.2's Dev Notes documented as "a natural, acceptable side effect" of load-and-mutate).

### What NOT to touch

- `GetFlatStructureFunction.cs`'s overall read shape — only add `RowVersion` to its `RoomResponse`/`PowerPointResponse` construction (Task 1.2); reads carry no data-loss risk, per Story 13.1's identical restraint.
- `Device`-related code paths anywhere in this story — Story 13.1 owns all of it; this story only removes `Devices` from the Room/PowerPoint write DTOs (already done by 13.1 if sequenced correctly) and never re-adds device handling to any of the three new endpoints.
- `DeviceAssignmentPeriod` cascade-delete behavior — unaffected; deleting a Room still cascades to its PowerPoints, their Devices, and those Devices' `DeviceAssignmentPeriod` rows exactly as today, via the existing `OnDelete(DeleteBehavior.Cascade)` chain.
- Room reordering / drag-to-reorder — does not exist in this codebase today and this story does not add it; `sortOrder` continues to be assigned from each room's current index in `draftRooms` at the moment it's saved, computed per-room now instead of via a full-array `.map()`.
