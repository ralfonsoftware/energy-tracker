# Adversarial Review — PRD: energy-tracker (2026-06-20)

- **Contract start date required/optional contradiction.** FR-4 and FR-6 both explicitly list "contract start date" as *optional* for the initial Tariff captured during Onboarding. But §4.4's feature description and FR-10 state "Each Tariff entry has a required contract start date," and FR-11/FR-13 depend on it as "the sole anchor for both cost-period resolution and price locking." The PRD never resolves what the system does for period-accurate costing (FR-13) or price locking (FR-11) if the Onboarding Tariff is saved without a contract start date — a gap in the one field the rest of §4.4 calls load-bearing.

- **§10 Open Questions cite decision-log IDs that resolve to unrelated entries.** Q-3 is annotated "*(UX D-13)*", Q-4 "*(UX D-17)*", Q-6 "*(UX D-18)*" — but `.decision-log.md`'s own D-13/D-17/D-18 entries are, respectively, about Eve Home `Datum` timestamp handling (FR-24), `locale-formats.md` authority (FR-41), and the §1 Vision framing edit — none related to Tariff-lock UX, budget placement, or Flat deletion. The actual matching decision-log entries are D-22/D-23/D-24. Two different documents evidently reuse the same "D-N" numbering for unrelated decisions with no disambiguation anywhere in the PRD, so anyone chasing the citation lands on the wrong record.

- **"Hub-free" is defined to include a claim the product itself violates.** §1 defines hub-free as "no always-on hardware, no cloud subscription, no direct API integration." The entire product is built exclusively on paid Azure cloud services — Static Web Apps, Functions, Blob Storage, Azure SQL (NFR-4 even quotes the ~€5/month SQL cost). As literally written, the principle is false of the very product it describes. It presumably means "no smart-hub-vendor cloud subscription" (Eve/Meross/Home Assistant), but the PRD never disambiguates "cloud subscription" from "Azure hosting."

- **FR-37's Budget Pressure Alert reintroduces the exact Tariff-noise problem FR-14 explicitly designed around.** FR-14 anchors the Dashboard's budget delta to kWh instead of euros specifically "since euro figures shift with every Tariff change and would make the delta incomparable across periods." FR-37, however, compares a euro-denominated rolling monthly cost projection against a static euro-denominated "planned annual spend" — so a mid-year Tariff price increase alone, with flat or even falling consumption, can push the projection over budget and fire a false "budget pressure" alert. FR-43 (invoice deviation) correctly anchors to kWh; FR-37 does not, and the inconsistency is never acknowledged.

- **Success Metrics were never extended past Release 2.** §7 lists SM-1 through SM-6, all validating FR-8 through FR-37. FR-44 through FR-55 — 12 of the document's 46 FRs, covering UI/behavior consistency, device lifecycle attribution, and insight dismiss/reactivate — have no corresponding Success Metric at all, despite §7 being the document's only stated mechanism for validating FRs.

- **`status: final` does not describe how this document actually behaves.** The front-matter has said `final` since 2026-06-20, yet §6 documents Release 3 "Added post-Epic-7 retro," Release 4 "Added 2026-08-01 via architecture review + brainstorming session, not the original PRD or a retrospective," plus two same-day `bmad-correct-course` insertions for FR-54 and FR-55. That's at least four rounds of post-finalization scope changes with no version-status field ever reflecting that this is a living document under continuous amendment.

- **A shipped trend-chart state is missing from FR-16/FR-17.** Epic 9 Story 9.8 ("Meter Reset Visual Indicator") added a third visual state to the trend chart — a `wasMeterReset` flag rendered as a distinct hatched/reset-icon bar wherever a reading drops below the prior one — as a resolved, shipped feature. FR-16/FR-17 still describe only two states ("A spike is visually encoded... the trend visualization reflects spike days distinctly from normal days"), so the PRD's own account of the trend chart is stale relative to the product it claims to specify.

- **Undocumented input-validation behavior.** Epic 9 Stories 9.7 ("Shared Decimal-Precision Validator Extension Method") and 9.11 ("Regression Test — KwhValue Precision Rejection") show the system rejects kWh submissions with excess decimal precision. No FR (FR-8, FR-24 through FR-31, etc.) specifies any precision or decimal-place constraint on numeric kWh input anywhere in the document — a real, user-facing rejection path with zero requirements-level grounding.

- **FR-27's reconciliation invariant is asserted as a fact, not a handled case.** "Attributed kWh across all plugs does not exceed the Main Meter total for any period" is stated unconditionally, but this is a property of imperfect real-world measurement, not something the system can guarantee — smart plugs can collectively over-report relative to the meter due to measurement error, which would produce a mathematically negative Residual. The PRD never states what happens in that case (clamp, flag, surface an error?), despite the Residual being one of only three named "design principles" (§1) and "always shown, never suppressed" (Glossary, FR-33).

- **FR-5's household-size kWh presets are uncited and inconsistently scaled.** Every other numeric constant in the document (2 W standby threshold, ±10% invoice-deviation threshold, ±1.0 kWh reconciliation tolerance, 7-day interpolation cap) is traced to a decision-log entry, `SPEC.md`, or an architecture/brainstorming session. FR-5's presets — 1,500 / 2,500 / 3,500 / 4,250 kWh for 1–4 persons — have no such citation anywhere, and the progression itself is odd (+1,000, +1,000, then only +750 for the 3→4-person step), reading like an arbitrary hand-picked figure dressed up with false precision rather than a sourced assumption.

- **Multi-user architecture is asserted with no FR ever exercising it.** §9 Platform and NFR-2 describe genuine per-user tenant isolation ("Single-tenant per authenticated user (keyed by user ID). No cross-tenant access.") and §1 Vision promises the architecture will accommodate "additional users" eventually — yet there is no FR anywhere for user registration, invitation, or account provisioning, and §2.2/§5 confirm there's no admin or multi-user UI. After 13 shipped epics of a single-owner deployment, this reads as unexercised architectural aspiration carried over from an early draft rather than a requirement grounded in any actual plan, and it's never revisited or pruned as the product matured.

- **FR-17's no-notification choice is never reconciled with the product's core emotional promise.** FR-17 explicitly states spike detection generates "No separate banner or notification" — visible only as a chart color change the user must proactively open the Insights tab to see. This sits directly against the stated emotional JTBD (§2.1: "Stop being surprised by my annual energy invoice") and Vision's promise to "know whether the month is tracking toward a surprising invoice before the invoice arrives" (§1). A silent spike is exactly the kind of event most likely to cause a surprise invoice, yet it's deliberately excluded from the notification-worthy category the four Insight types already occupy, with no rationale given for the asymmetry.

- **Versioning-scheme drift between sections.** §2.2 ("Non-Users (v1)") and §5 ("Support for smart plug brands other than Eve Home and Meross in v1/v2") still use a "v1/v2" scope label, while §6 has moved to a four-"Release" model that doesn't map cleanly onto "v1/v2." Since Releases 3 and 4 were added after this Non-Goal was written and the Non-Goals section was never revisited, it's ambiguous whether "in v1/v2" was meant to also bind Releases 3/4 or whether the exclusion has quietly narrowed in scope.

- **The SPEC-governs-on-conflict rule has no maintained tripwire.** §0 states "The SPEC is the canonical contract; where this PRD and the SPEC differ, the SPEC governs" — but the PRD gives no mechanism for detecting such a difference, and after 13 epics and at least six documented post-hoc amendments to this PRD (Releases 3/4, FR-44 through FR-55), there is no evidence anywhere in this document that `SPEC.md` was re-synced alongside any of them. The canonical/subordinate relationship is asserted once and never demonstrably maintained.

- **Interaction between date-aware attribution (FR-52/FR-53) and interpolation (FR-26) is unspecified.** FR-52 gates Decomposition inclusion by `InUseSince`/`DecommissionedDate`, and FR-53 splits a reassigned Device's consumption by Room per day — but neither FR states whether this date-gating happens before or after a gap is filled by linear interpolation, nor how an interpolated day that spans a reassignment boundary should be split. Three separately-shipped features (Epic 6 interpolation, Epic 12 date-aware attribution) touch the same daily-value pipeline with no stated ordering or interaction rule.
