## What Went Well

- **Stub-contract-first design (Story 10.1).** The `DetectAsync(flatId, runId, ct)` signature was locked before any real detector logic existed. Stories 10.2 and 10.3 dropped in real detection logic without touching `ProcessInsightsFunction`'s call sites at all — deliberate boundary discipline paid off even in a codebase with zero custom interfaces.
- **Code review earned its keep, every time.** Adversarial review found and fixed real bugs in all four stories: 9 patches (10.1), 7 patches (10.2), 6 patches (10.3), 9 patches + 1 resolved decision (10.4). Never a rubber stamp.
- **Reuse over duplication on the frontend.** Story 10.4 extended the existing `TrendChart` component (Epic 3) to support 30/90-day windows instead of forking a new component, keeping `ReadingHistorySheet` integration free.
- **Clean incident response.** When Story 10.1's deploy failed in CI/CD (SQL Server Error 1785), the team wrote a proper investigation doc, reproduced the failure against a disposable local SQL Server container (not live Azure), and verified the fix there before redeploying.
- **Ralf's own read:** the detector accuracy/quality itself stood out — the insights feel useful and correctly calibrated on real data, which is the actual point of FR-35–FR-39.

## Challenges & Patterns

- **`ResolveTariff` is now duplicated across 6 independent files.** `TariffResolver` was correctly deleted as dead code per Epic 9's retro Action Item #5. But nothing replaced it with a shared utility, so Epic 10's four new detectors re-duplicated the identical tariff-resolution logic (including its known arbitrary tie-break bug on equal `ContractStartDate`) on top of the two existing copies in `KpiCalculator`/`DecompositionEngine`. Each story's Dev Notes correctly said "duplicate verbatim, don't extract a shared utility" for that story in isolation — but nobody stepped back at the epic level to ask whether six copies changes the calculus. **Lesson:** correct per-story decisions can compound into debt nobody explicitly chose; second-order effects of closed action items need epic-level tracking, not just story-level.
- **Story 10.1's SQL Server multi-cascade-path deploy failure.** The dev had already reasoned through and correctly handled one nullable-FK cascade risk (`Insight.DeviceId` → `SetNull`, with an explicit code comment). The identical risk class existed on the sibling `Insight.RunId` FK in the same entity and wasn't checked — it only surfaced when the actual Azure SQL migration deploy failed (Error 1785). Root-caused and fixed same day via `ClientSetNull` on both edges, verified against a local SQL Server container first. **Lesson:** when an entity has multiple nullable FKs into a cascade-heavy schema, check all of them together in one pass, not one at a time as they're written.
- **A genuine AC-precedence bug in Story 10.4**, caught by code review before merge: the discovery-progress indicator and the "no findings" empty-state text would have rendered simultaneously on a flat's very first run (before any insight ever existed) — an easy state to miss manually since it only appears once, pre-first-run.
- **Recurring test-naming-vs-assertion mismatches.** Story 10.1 had a test named for a `Processing`-status transition it never actually asserted; Story 10.4 had one named for a "distinct cache key" that only checked a function call argument. Same mistake pattern, two different stories, months apart — low severity, caught every time by review, but recurring.

## Key Takeaways

1. The stub-contract-first design in Story 10.1 let three later stories drop in real logic with zero rework — deliberate boundaries pay off even without formal interfaces.
2. Correct decisions made in isolation can compound into debt nobody explicitly chose — epic-level rollups of closed action items' second-order effects are needed, not just story-level tracking.

4. The adversarial code-review process found genuine, non-trivial bugs in all four stories of this epic — it is earning its keep, not acting as a rubber stamp.
