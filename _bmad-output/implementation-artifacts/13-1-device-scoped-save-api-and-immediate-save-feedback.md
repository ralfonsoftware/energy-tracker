# Story 13.1: Device-Scoped Save API & Immediate Save Feedback

Status: ready-for-dev

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a user editing my flat's devices,
I want clicking Save on the device edit page to immediately persist that one device and tell me whether it worked,
so that a device I save is never silently lost because of an unrelated save happening elsewhere, and I always know for certain whether my change is safe.

## Acceptance Criteria

1. **Given** devices are currently created/updated only as part of `UpdateFlatStructureFunction.cs`'s whole-flat replace payload, with no standalone endpoint, **when** implemented, **then** new dedicated Functions exist following this codebase's established per-verb Function pattern (mirroring `Features/Tariffs/CreateTariffFunction.cs`'s shape: tenant ownership check via `db.Flats`/`db.PowerPoints` lookup, Problem Details errors, `CancellationToken` threaded through): `POST /v1/flats/{flatId}/powerpoints/{powerPointId}/devices` (create — returns `201` with the new `DeviceResponse`, including a real `DeviceId` and a freshly-seeded open `DeviceAssignmentPeriod` exactly as `UpdateFlatStructureFunction.cs`'s existing new-device branch does today at lines 227-257), `PUT /v1/flats/{flatId}/powerpoints/{powerPointId}/devices/{deviceId}` (update all editable device fields — name, type, manufacturer, model, purchaseDate, inUseSince, decommissionedDate, consumptionApproach and its dependent fields — returning `200` with the updated `DeviceResponse`; if `powerPointId` differs from the device's current one, closes the current open `DeviceAssignmentPeriod` and opens a new one, exactly as the existing reassignment branch does today at lines 209-222), and `DELETE /v1/flats/{flatId}/powerpoints/{powerPointId}/devices/{deviceId}` (deletes the device; EF cascade delete already handles its `DeviceAssignmentPeriod` rows per `DeviceConfiguration.cs`'s existing `OnDelete(DeleteBehavior.Cascade)`).
2. **Given** these three endpoints each use EF Core's `RowVersion` concurrency token already present on `Device` (`DeviceConfiguration.cs:27`, currently unused for concurrency checks anywhere in the codebase), **when** implemented, **then** the update and delete endpoints require the client to send back the device's current `rowVersion` (matching this codebase's established `ApplyRowVersionCheck`/`TryParseRowVersion` pattern from `Shared/ConcurrencyExtensions.cs`) and return `409 Conflict` Problem Details on a mismatch — this is the endpoint-level backstop that makes a genuinely concurrent edit to the *same* device fail loudly instead of silently.
3. **Given** `UpdateFlatStructureFunction.cs` currently treats a device absent from its payload as deleted, and a device present-with-no-`deviceId` as new, **when** implemented, **then** device create/update/delete is removed entirely from `UpdateFlatStructureFunction.cs`'s write semantics — the `Devices` array is no longer read from the request body at all (any devices arriving in a room/power-point's payload are ignored for writes; `GetFlatStructureFunction.cs`'s response is unaffected and continues returning devices nested under their power point exactly as today, since reads carry no data-loss risk) — such that no whole-flat save can ever create, modify, or delete a device again, regardless of what any tab's stale snapshot contains.
4. **Given** `DeviceEditor.tsx`'s Save button currently only calls its `onSave` prop (pure local state update via `FlatStructureEditor.tsx`'s `handleUpdateRoom`, no network call), **when** implemented, **then** a new `useSaveDevice` hook (`client/src/features/flat-structure/hooks/useSaveDevice.ts`, one hook per mutation per this project's established convention) wraps the three new endpoints behind a single `mutate` call that picks POST vs. PUT based on whether the device being edited has an existing `deviceId`, and `DeviceEditor.tsx`'s Save button calls this hook directly — the device is persisted (or the save fails) the instant this button is clicked, no longer deferred to a later room/page-level save.
5. **Given** this project's established mutation-feedback convention (`mutation.error.detail` displayed as a banner near the Save button, distinct from field-level `form.formState.errors`; success acknowledged inline, matching `RoomEditor.tsx`'s existing `saveError`/`saveSuccess` treatment in its `StickyActionBar`), **when** implemented, **then** `DeviceEditor.tsx` shows an explicit inline success message on `onSuccess` and an explicit inline error banner (using `mutation.error.detail`) on `onError` near its own Save button, staying open (not returning to the room view) on failure so the user can retry without re-entering data — matching this codebase's established "mutation errors: sheet/form stays open" convention.
6. **Given** the removal of devices from `UpdateFlatStructureFunction.cs`'s write path, **when** implemented, **then** `FlatStructureEditor.tsx`'s local state management for devices is updated to match: the `DeviceEditor` `onSave` wiring no longer calls `handleUpdateRoom` to locally splice the device into `draftRooms` before a later save — instead, the new `useSaveDevice` mutation's `onSuccess` updates the query cache directly (e.g. `queryClient.setQueryData`/`invalidateQueries` scoped to `['flat-structure', flatId]`, per this codebase's established TanStack Query convention) so the already-persisted device flows back into `draftRooms` via the normal data flow, and `PowerPointEditor.tsx`'s existing device-delete confirm flow is wired to call the same hook's delete path immediately (also no longer deferred to a later structural save).
7. **Given** the new endpoints and the removal of devices from the old endpoint's write path, **when** tested, **then** new `api.Tests/Features/FlatStructure/` test files cover each new Function's `RunAsync` directly (success, tenant-check 403, validation 400, `RowVersion` conflict 409, and — for create — the fresh `DeviceAssignmentPeriod` seeding; for update-with-reassignment — the period-close/period-open pair, mirroring the existing coverage pattern in `UpdateFlatStructureFunctionTests.cs`), `UpdateFlatStructureFunctionTests.cs`'s existing device-related test cases are updated or removed to reflect that this endpoint no longer processes `Devices` (room/power-point-only cases continue to pass unmodified), and a new frontend test in `DeviceEditor.test.tsx` (or a new `useSaveDevice.test.ts`) asserts the Save button triggers the network call and both the success and error feedback paths render.

## Dev Notes

- **This story is entirely sourced from a Confirmed production investigation, not the PRD.** Read `_bmad-output/implementation-artifacts/investigations/structure-editor-device-not-persisted-investigation.md` in full before starting — it contains the exact reproduction, the live request/response bodies captured, and the precise reasoning for why this fix (not a smaller patch) is required. The investigation's "Follow-up: 2026-08-02 #2" section is the most load-bearing part.
- **Root cause being closed:** `UpdateFlatStructureFunction.cs` fully replaces the flat's room/power-point/device tree per request — anything absent from the payload is deleted. `FlatStructureEditor.tsx` seeds its local edit snapshot once per mount and never resyncs it. A save from a tab holding an older snapshot silently deletes devices added elsewhere. This story closes it for devices specifically by taking devices out of the whole-flat payload's write semantics entirely — there is no longer a "stale snapshot" to worry about for devices, because a device save is now its own atomic, immediately-effective request scoped to exactly one device.
- **`DeviceResponse` is missing `RowVersion` today** (`api/Features/FlatStructure/FlatStructureModels.cs:5-18`) even though `Device.RowVersion` exists on the entity. This must be added (Task 1) before the update/delete endpoints' concurrency check (AC #2) is possible — the frontend cannot send back a `rowVersion` it was never given.
- **Reuse, don't reinvent, the `DeviceAssignmentPeriod` logic.** The exact create-with-fresh-period and reassign-closes-old-opens-new logic already exists and is already tested in `UpdateFlatStructureFunction.cs:209-257` — copy it into the new Functions rather than re-deriving it. Get the constant `now = DateTimeOffset.UtcNow` captured once per request, same as today.
- **`UpdateFlatStructureValidator.cs`'s per-device `ChildRules`** (currently lines ~21-46 per this codebase's current state) must become a standalone `DeviceValidator : AbstractValidator<DeviceInput>` shared by the three new Functions and no longer referenced by `UpdateFlatStructureValidator` — do not duplicate the validation rules by hand-copying them into three places.
- **Do not touch `GetFlatStructureFunction.cs`'s read behavior** beyond adding `RowVersion` to its `DeviceResponse` construction — it already correctly returns devices nested under their power point and carries zero data-loss risk (reads never delete anything). This story's entire risk surface is on the *write* side.
- **`api/Data/Entities/DeviceAssignmentPeriod.cs`** and its migration-added filtered unique index (`IX_DeviceAssignmentPeriods_DeviceId_OneOpenPeriod`, one open period per device) are unaffected by this story — the new Functions must respect this constraint exactly as the old code already does (close-before-open, never two opens at once).
- **`Device.PowerPointId` is `IsRequired()` with `OnDelete(DeleteBehavior.Cascade)`** from `PowerPoint` (`DeviceConfiguration.cs:14,28-31`) — deleting a `PowerPoint` still cascades to its `Devices` (and their `DeviceAssignmentPeriod`s) exactly as today; this story does not change `PowerPoint`/`Room` deletion behavior, only direct device-level create/update/delete.
- **Frontend mutation convention (non-negotiable per project-context.md):** `await queryClient.invalidateQueries(...)` in `onSuccess` — never fire-and-forget, since `DeviceEditor` navigates back to the room view immediately after a successful save and could unmount mid-invalidation otherwise. `mutation.error.detail` (typed `Error & { detail?: string }`) is the source for the error banner text — never `form.formState.errors`, which stays reserved for field-level zod validation.
- **`DeviceEditor.tsx`'s existing local-only validation** (`isSaveEnabled`, name/kWh/date-range checks, lines 66-71 of the current file) stays exactly as-is and continues to gate the Save button client-side *before* the network call — this story adds a network call and its feedback on top of the existing client-side gate, it does not replace it.
- **Do not add this story's new endpoints' error handling via a blanket `catch (DbUpdateException)`** the way `UpdateFlatStructureFunction.cs` does today (already flagged as a pre-existing gap in `deferred-work.md:461-462` — any unrelated `SaveChangesAsync` failure gets misreported as a PlugId conflict there). For the new, narrower endpoints, catch `DbUpdateConcurrencyException` specifically for the `409` rowVersion-mismatch case; a genuinely unexpected `DbUpdateException` should be allowed to propagate as an unhandled 500 rather than be mislabeled, consistent with there being no PlugId-conflict-shaped ambiguity at the single-device scope.
- **Out of scope for this story:** Story 13.2 (room/power-point scoping) is a separate follow-on — do not attempt to also scope room/power-point saves here. The `UpdateFlatStructureFunction.cs` endpoint continues to exist and continues to handle room/power-point create/update/delete after this story; it just stops touching devices.

### Project Structure Notes

- New backend files land in the existing `api/Features/FlatStructure/` folder, alongside `UpdateFlatStructureFunction.cs`/`GetFlatStructureFunction.cs`/`UpdateFlatStructureValidator.cs` — this is a feature-folder-by-domain codebase (VSA), not by HTTP verb, so `CreateDeviceFunction.cs`/`UpdateDeviceFunction.cs`/`DeleteDeviceFunction.cs`/`DeviceValidator.cs` all belong in this same folder, matching how `Features/Tariffs/` holds `CreateTariffFunction.cs`/`PatchTariffFunction.cs`/`GetTariffsFunction.cs`/`TariffValidator.cs`/`PatchTariffValidator.cs` together.
- New frontend files: `client/src/features/flat-structure/hooks/useSaveDevice.ts` (and `useDeleteDevice.ts`) alongside the existing `useFlatStructure.ts`/`useUpdateFlatStructure.ts` — this project's mandatory `hooks/`/`api/`/`components/`/`schemas/` per-feature subdirectory structure is already in place for this slice, just add the new hook file(s) to the existing `hooks/` folder.
- No new npm/NuGet dependencies required — this story is entirely new usages of already-present patterns (FluentValidation, EF Core, TanStack Query `useMutation`).
