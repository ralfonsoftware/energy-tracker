# Story 12.2: Device Room-Assignment History — Date-Aware Decomposition Attribution

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a user,
I want the app to remember which room a device was in when I move it,
so that my Decomposition figures correctly split its consumption across the rooms it actually occupied during a query period, without me having to enter any dates manually.

## Acceptance Criteria

1. **Given** a new `DeviceAssignmentPeriod` entity, **when** reviewed, **then** `DeviceAssignmentPeriodConfiguration.cs` defines `Id` (guid PK), `DeviceId` (FK to `Device`, cascade delete — the *only* cascading relationship on this table, see Dev Notes for why), `PowerPointId` (plain `Guid`, **not** a formal FK relationship), `FlatId` (plain `Guid`, **not** a formal FK relationship — denormalized for query convenience only, mirroring `PowerPoint.FlatId`'s existing precedent), `From` (`DateTimeOffset`), `To` (`DateTimeOffset?`, `null` = current/open period); Fluent API only; index on `(DeviceId, From)`.

2. **Given** the migration introducing this table, **when** applied, **then** it backfills one open-ended period per existing `Device` — `From = Device.InUseSince ?? DateTimeOffset.MinValue` (see "Gap found during story creation" #1 for why this differs from the epic's literal text), `PowerPointId` = the device's current value, `FlatId` = the device's current `PowerPoint.FlatId`, `To = null` — so no existing device disappears from Decomposition once room resolution switches to period-based lookup.

3. **Given** `UpdateFlatStructureFunction`'s save path, which today deletes every `Room`/`PowerPoint`/`Device` row for the flat and reinserts brand-new rows (fresh GUIDs) on **every** save regardless of what actually changed, **when** implemented, **then** the save path is reworked into an identity-preserving upsert: incoming `RoomInput`/`PowerPointInput`/`DeviceInput` payloads carry an optional `roomId`/`powerPointId`/`deviceId`; a row is matched and updated in place when its ID is present and matches an existing row scoped to this flat, inserted as new when the ID is absent/unmatched, and any existing row whose ID is no longer present in the incoming payload is deleted (with normal cascade behavior). This is a precondition for AC4/AC5 — see "Gap found during story creation" #2 for why the epic's literal AC3 text (below) is otherwise impossible.

4. **Given** the now-identity-preserving `UpdateFlatStructureFunction` (AC3), **when** a *matched* Device's incoming `PowerPointId` differs from its currently persisted value, **then** the open `DeviceAssignmentPeriod` for that Device is closed (`To = now`) and a new one is inserted (`From = now`, new `PowerPointId`) — fully automatic, no UI or manual date entry; a brand-new Device (unmatched, freshly inserted) gets its first period seeded with `From = Device.InUseSince ?? now`. A matched Device whose `PowerPointId` is unchanged is updated in place with no assignment-period side effect.

5. **Given** `DecompositionEngine.cs`'s room-grouping, **when** computing a period, **then** each Device's daily kWh/cost — both the measured path (`pp.PlugId is not null && pp.Devices.Count == 1`) and Story 12.1's window-gated estimated path (the standalone `else` branch) — is attributed per day to whichever Room its resolved `PowerPointId` belongs to on that day, resolved via a new `DeviceAssignmentResolution.Resolve` helper following the same "latest period with `From <= date`" idiom already established by `TariffResolution.Resolve`.

6. **Given** a Device whose room changed mid-period, **when** the Decomposition response is built, **then** the Device appears under each Room it occupied, each with its own `DeviceDecomposition` entry scoped to the days it belonged there — partial totals across Rooms sum to the Device's correct period total.

7. **Given** Smart Power Strip sub-devices (`BuildSmartStripDecomposition`'s pool-math branch, `pp.Devices.Count > 1`), **when** computing a period, **then** this story's day-by-day room resolution does **not** apply to them — sub-device shares continue using whole-period, current-structure-snapshot math exactly as today; a sub-device moving strips (or a device moving into/out of a strip) mid-period is explicitly out of scope, tracked as a follow-up (same rationale as Story 12.1's AC4).

8. **Given** `DecompositionEngine.cs`'s decimal divisions (`EuAnnualKwh / 365m`, `SelfMeasuredKwh / 7m`, and the Smart Power Strip per-share pool-math divisions) propagating full, unbounded decimal precision into the JSON response today, **when** implemented, **then** every `Kwh`/`Cost` figure in the final `DecompositionResponse` (Total, Residual, each `RoomDecomposition`, each `DeviceDecomposition`/`SubDeviceDecomposition`) is rounded to 4 decimal places (`Math.Round(value, 4, MidpointRounding.AwayFromZero)`) at the point of DTO construction — see "Gap found during story creation" #4 for why this belongs in this story, not Story 12.1.

9. **Given** extended `DecompositionEngineTests.cs`, `UpdateFlatStructureFunctionTests.cs`, and new tests for `DeviceAssignmentResolution`, **when** run, **then** tests cover: no room change (unaffected, regression guard); one mid-period move (correct per-room split, totals preserved); pre-existing device with only its backfilled period (unchanged behavior); migration backfill correctness; identity-preserving upsert (matched rows update in place and keep their DB identity/RowVersion progression; unmatched incoming rows insert as new; existing rows absent from the payload are deleted); a `PowerPointId` change on a matched Device closes/opens periods correctly; the decimal-rounding fold-in (a non-terminating division rounds to exactly 4 places in the response).

### Gap found during story creation

Four corrections/additions to the epic's original text (`epics/epic-12-device-lifecycle-and-date-aware-decomposition-attribution.md#Story 12.2`) and its cross-references, found by reading the actual current-state code rather than trusting the epic's/architecture doc's prose:

**1. `Flat.CreatedAt` does not exist.** The epic's migration-backfill AC reads `From = Device.InUseSince ?? Flat.CreatedAt`, and `architecture.md`'s own entity-model table for `Flats` (line 222) lists only `FlatId, UserId, Name, AnnualKwhBaseline, SpikeThreshold, PlannedAnnualSpend` — no `CreatedAt`. `api/Data/Entities/Flat.cs` confirms this (5 properties, no timestamp). Only `Insight` and `ImportJob` have a `CreatedAt` column anywhere in this codebase. Adding a `CreatedAt` column to `Flat` purely to serve as a backfill fallback would expand this story's scope onto an entity Epic 12 doesn't otherwise touch, for a value whose only purpose is "a date safely before any real query the user might run." AC2 uses `DateTimeOffset.MinValue` instead — SQL Server's `datetimeoffset` column type supports `0001-01-01T00:00:00+00:00` as a valid value, and it achieves the identical practical goal (guarantee no pre-existing device's estimated/measured kWh silently vanishes from any real-world Decomposition query) without touching `Flat`.

**2. The single biggest gap: `UpdateFlatStructureFunction`'s full-replace save path makes the epic's literal AC3 impossible today, and fixing it is this story's largest task.** The epic's AC3 says: "When a Device's incoming `PowerPointId` differs from its currently persisted value, the open `DeviceAssignmentPeriod` for that Device is closed... and a new one is inserted." This assumes the backend can recognize "this incoming Device *is* that persisted Device" — but it can't, because:
   - `DeviceInput` (`FlatStructureModels.cs`) has no `DeviceId` field at all, and neither `PowerPointInput` nor `RoomInput` carry their respective IDs either.
   - `UpdateFlatStructureFunction.RunAsync` (lines 98-130) always does `db.Rooms.RemoveRange(existingRooms)` followed by `db.Rooms.AddRange(newRooms)` — **every** save deletes every Room/PowerPoint/Device for the flat and reinserts them with brand-new EF-generated GUIDs, regardless of whether anything relevant actually changed (e.g., renaming one unrelated Room blows away and recreates *every* Device in the flat).
   - Client-side, `draftModel.ts`'s `DraftDevice` has no `deviceId` field, and `DraftPowerPoint.powerPointId` is captured from the server response but its own comment (line 33-34) states it is "never sent back to the server." `DraftRoom` doesn't capture `roomId` at all.
   - Since `Device`/`PowerPoint`/`Room` are all cascade-children in a chain (`Device -> PowerPoint -> Room -> Flat`, all `OnDelete(Cascade)`), a `DeviceAssignmentPeriod` FK'd to `DeviceId` would cascade-delete on the very next save that touches *any* part of the flat's structure — even one completely unrelated to the device in question — making persistent assignment history structurally impossible without first fixing identity preservation. This isn't a design choice; there's no way around it given the current schema and save path.

   Resolution (AC3, and the corresponding rework in Tasks below): `UpdateFlatStructureFunction` is reworked into a genuine ID-matched upsert across all three levels (Room, PowerPoint, Device), and the client is updated to round-trip `roomId`/`powerPointId`/`deviceId` for existing entities (new entities still omit them, exactly as today). This is a materially larger change than the epic's text implies, but it's the *only* way AC4 (the epic's literal AC3) can function at all — without it, "fully automatic, no UI or manual date entry" tracking would reset on every unrelated Flat Structure edit. Existing tests that send payloads with no IDs at all (simulating a fully-replaced structure) continue to pass unmodified under this design — see `UpdateFlatStructureFunctionTests.RunAsync_ReplacingExistingStructure_RemovesOldRoomsPowerPointsAndDevices`, which seeds old rows never referenced by ID in the request payload and asserts they're gone after save; that assertion holds under upsert semantics too, since "ID absent from payload" and "ID doesn't match anything" both correctly fall through to delete-old/insert-new.

**3. `DeviceAssignmentPeriod.FlatId` must *not* be a cascading FK relationship, or the migration will fail to create the table.** The epic's own architecture note (`architecture.md:228`) lists `FlatId FK` alongside `DeviceId FK` and `PowerPointId FK` as if all three are ordinary cascading foreign keys. If `FlatId -> Flat` were configured `OnDelete(Cascade)` *in addition to* the `DeviceId -> Device -> PowerPoint -> Room -> Flat` cascade chain, SQL Server would reject the schema at creation time with a "may cause cycles or multiple cascade paths" error (Error 1785) — two independent cascade paths would both lead from `Flats` into `DeviceAssignmentPeriods`. This is exactly the class of bug the Epic 10/11 retrospective's Action Item #2 ("check all nullable-FK cascade paths together") was about, and this codebase has hit this **exact** error before, twice, on the same table: `InsightConfiguration.cs` (lines 26-50) documents Error 1785 being hit "confirmed empirically" for both `Insight.DeviceId` (`Flat -> Room -> PowerPoint -> Device -> Insight` vs. the direct `Flat -> Insight` cascade) and `Insight.RunId` (`Flat -> InsightRun -> Insight` vs. the same direct cascade) — both resolved with `OnDelete(DeleteBehavior.ClientSetNull)` instead of `Cascade`/`SetNull`. `DeviceAssignmentPeriod.FlatId` is the identical shape of conflict (`Flat -> Room -> PowerPoint -> Device -> DeviceAssignmentPeriod` vs. a hypothetical direct `Flat -> DeviceAssignmentPeriod` cascade), so this story follows the *simpler* of this codebase's two established precedents for it: `PowerPoint.FlatId` (added in Story 11.3, `PowerPointConfiguration.cs`) is a plain, unconstrained `Guid` column — no `HasOne(pp => pp.Flat)` navigation, no FK constraint at all (not even `ClientSetNull`, since nothing needs to null it out) — purely denormalized for query/index convenience, letting the *single* real cascade path (`PowerPoint -> Room -> Flat`) do the deleting. `ClientSetNull` isn't needed here the way it is for `Insight.DeviceId`/`RunId`, because those are meaningful nullable references that must survive their target's deletion; `DeviceAssignmentPeriod.FlatId` is pure denormalization with no independent meaning once its owning `Device` is gone. AC1 follows the `PowerPoint.FlatId` pattern for both `FlatId` and `PowerPointId` on `DeviceAssignmentPeriod`: `DeviceId -> Device` is the *only* formal relationship; `PowerPointId` is also intentionally left as a plain, unconstrained column (not just for the cascade-path reason, but because a `Restrict`/`NoAction` FK there would *block* deleting a PowerPoint that any historical — even closed — assignment period still references, breaking the ordinary "delete this Power Point, add a different one" editing flow). One accepted consequence: a *closed* `DeviceAssignmentPeriod` can end up referencing a `PowerPointId` for a PowerPoint that's since been deleted (the Device itself moved elsewhere and still exists; the old, now-empty PowerPoint was later removed). `DecompositionEngine`'s day resolution handles this defensively (see Dev Notes) but the historical room attribution for those old days becomes best-effort, not exact — this is judged an acceptable, low-probability edge case, not a new AC, consistent with how Story 12.1 deferred comparably-shaped edge cases.

**4. The decimal-rounding-policy fold-in, explicitly deferred here by Story 12.1.** The Epic 11 retrospective (`_bmad-output/implementation-artifacts/epic-11-retro-2026-08-01.md`, Action Item #2: "Fold the Decomposition decimal-rounding-policy gap into Story 12.1/12.2") and Story 12.1's own Dev Notes ("Deferred to Story 12.2 instead... flag this explicitly when Story 12.2 is created so the fold-in isn't lost a second time") both point here. The underlying `deferred-work.md` entry (line 398, sourced from Story 7.1's review): "No rounding policy applied to decimal divisions (`EuAnnualKwh / 365m`, `SelfMeasuredKwh / 7m`, per-day/per-share splits) before they reach the JSON response — full decimal precision propagates through." AC8 implements this as a single rounding pass applied only at final DTO-construction boundaries (not on intermediate per-day terms feeding a sum, which would compound rounding error) — see Dev Notes for the exact placement. No existing precedent for rounding mode exists anywhere in this codebase (`grep -rn "Math.Round" api/` returns nothing) — `MidpointRounding.AwayFromZero` is used explicitly rather than `Math.Round`'s default (banker's/`ToEven`) rounding, both because it's the more intuitive convention for user-facing figures and because `deferred-work.md` (line 16) separately flags that relying on the *implicit* default is exactly the kind of ambiguity that's already caused test-coverage gaps elsewhere (`DecimalPrecisionTruncationTests`).

## Dev Notes

### Why this story exists

Epic 12 (`epics/epic-12-device-lifecycle-and-date-aware-decomposition-attribution.md`) is sourced from an architecture review and a brainstorming session, not the original PRD or a retrospective action item (see Story 12.1's own Dev Notes for the full background). This is the second of Epic 12's four stories, building on Story 12.1's `InUseSince`/`DecommissionedDate` existence-window gating. Where 12.1 answered "is this device active at all on day X," 12.2 answers "which Room was this device's consumption attributed to on day X" — the two are independent day-gates that both narrow down a device's estimated (or, for the first time in 12.2, *measured*) kWh contribution on a given day.

### Current state of `DecompositionEngine.cs`'s room-grouping (read in full during story creation)

`ComputeAsync`'s outer loop (`api/Features/Decomposition/DecompositionEngine.cs:81-137`) is structurally room-first: it iterates `rooms` (loaded via `db.Rooms.Include(PowerPoints).ThenInclude(Devices)`, a live structural snapshot), and for each `PowerPoint` within each `Room`, branches on `PlugId`/`Devices.Count` into four cases — measured-single (line 87), Smart Power Strip (line 97), orphaned-plug (line 101), and standalone-estimate (line 107, the branch Story 12.1 modified). Every branch today attributes 100% of a device's period kWh/cost to whichever `Room` it *currently, structurally* belongs to — there is no per-day room resolution anywhere in this file before this story.

### The `TariffResolution` precedent `DeviceAssignmentResolution` must follow

`api/Shared/TariffResolution.cs` (full file, 29 lines) is the exact template: `Resolve(IReadOnlyList<T> items, DateTimeOffset date)` picks the item with the latest qualifying date `<= date` (inclusive), tie-broken deterministically by a secondary key (`TariffId.CompareTo`) so behavior never depends on the input list's enumeration order. `DeviceAssignmentResolution.Resolve` follows the identical shape, with one addition `TariffResolution` doesn't need: it must also check `To is null || date <= To`, since (unlike `Tariff`, which has no end date) a `DeviceAssignmentPeriod` can be closed.

### The identity-preserving upsert — why it's this story's real center of gravity

See "Gap found during story creation" #2 above for the full reasoning. The short version for anyone skimming: today, `UpdateFlatStructureFunction` treats every save as "the whole flat structure was just deleted and rebuilt from scratch," so no `Device`/`PowerPoint`/`Room` row's primary key survives from one save to the next. A `DeviceAssignmentPeriod` history keyed by `DeviceId` cannot survive that. Task 3 is the fix, and it is the largest, highest-risk piece of this story — a bug in the diff/merge logic risks silently corrupting or losing Flat Structure data (a much more sensitive failure mode than a wrong Decomposition number). Test it thoroughly (Task 7.3) before moving on to Tasks 4-6.

### Why `PowerPointId`/`FlatId` on `DeviceAssignmentPeriod` are plain columns, not FKs

See "Gap found during story creation" #3. This is the same class of issue the Epic 10/11 retrospective's Action Item #2 exists to catch — always trace *every* cascade path into a table before adding a new FK relationship, not just the one the current change is "about."

### What NOT to touch

- `EstimateDailyKwh` (line 241-248) and `ResolveStandaloneApproach` (line 250-256) — untouched; Task 6's rounding happens at DTO construction, not inside these.
- `IsDeviceActiveOn` (line 261-263, Story 12.1) — untouched; Task 5's day loop still calls it exactly as today for the estimate path.
- `BuildSmartStripDecomposition` (lines 183-239) internals — untouched (AC7); only *how its output gets merged into `deviceDecompositionsByRoom`* changes structurally (Task 5.4), not its own math.
- `TryComputeMainMeterTotal`/`BuildMainMeterDailySeries` (lines 266-306) — unrelated to per-device room attribution.
- `DeviceEditor.tsx`'s date-field UI (Story 12.1) — this story adds no new UI; `Device` room assignment is entirely inferred from the existing "which `PowerPointInput` is this device nested under" signal already present in every save, per AC3/AC4. Do not add any new UI control for room-assignment history — FR-54/AD-8b are explicit that this is automatic.
